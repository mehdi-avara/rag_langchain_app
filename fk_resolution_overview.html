The search seam (function now, HTTP later)

# resolver depends ONLY on this interface — swapping the impl changes no caller class SearchProvider(Protocol): def search(self, *, db, user, query, ids=None, limit=10) -> list[Candidate]: ... FunctionSearchProvider(search_card_hits, _card_to_candidate) # ← TODAY (in-process call) HttpSearchProvider("/financial_management/cards/search") # ← FUTURE (drop-in, no caller change)
Each module exposes interface functions (search_card_hits, search_customer_hits) extracted out of the route handlers. The route calls them; the assistant calls the same ones. To go HTTP, register a different provider for the resource — nothing else moves.

Three outcomes per reference

resolved

One strong match. The id is auto-filled into the draft payload; the label is shown so the user can override.

"Ali's Mellat card" → 1 match ✓ credit_card_id = 12 label: "Mellat — ••••4821 — Ali Rezaei"

ambiguous

Several plausible matches. No id is filled. Best guess is the default chosen; up to 5 alternatives ride along for the user to pick.

"Ali's card" → 3 matches ⚠ references_pending: ["credit_card_id"] chosen + alternatives[]

missing

No match. Carries a create_suggestion (endpoint + inferred fields). Frontend creates it, then reports the new id back.

"Sina Trading Co" → 0 matches ✗ create_suggestion: POST /…/customers { name: "Sina Trading Co" }

A draft with anything in references_pending is still sent and persisted — the frontend just can't commit until that list is empty.

Missing → create → callback

Backend (draft)
  1. Reference resolves to missing
  2. Attaches create_suggestion with the create endpoint + inferred payload
  3. Streams draft with references_pending
⇄
Frontend
  1. Offers "create this record"
  2. Calls the module's own create endpoint → gets new id
  3. PATCH /assistant/drafts/{id} with resolved_references: { customer_id: { id, label } }
  4. Server writes id into payload, flips ref to resolved, clears pending → commit
