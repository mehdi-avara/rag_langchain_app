1 · Purchase flow — whole flow

Owner/actor is shown under each box. The chain is a sequence of FK references; the only place data crosses a module boundary asynchronously is goods_receipt → warehouse via the Celery task on_grn_posted.

Seam detail. post_goods_receipt calls purchase_management.apply_goods_receipt in-process, sets GRN status POSTED, commits, then fires the Celery event on_grn_posted.delay(grn.id). The warehouse side runs in a separate transaction/worker. goods_receipt_management/services.py:819–839, warehouse_management/tasks.py:28–35.

3 · Warehouse flow — whole flow

The warehouse module never reads purchase/GRN models directly. The Celery task pulls a plain dict via get_posted_goods_receipt_for_warehouse and writes two things: an immutable stock_movements ledger row (the delta) and the running stock_items balance (weighted-average cost).

5 · Which states can be bypassed now

Bypassability is read off the schema (which linking FK is nullable / what free-text fallback exists) and any service guard that blocks the path. Each card states the evidence.

Skippable

① Material Requisition

Nothing downstream hard-requires an MR. rfqs.mr_id is nullable, and a PO can be created with no MR/RFQ at all.

Evidence: rfq_management/models.py:57–61 (mr_id SET-NULL nullable); manual PO endpoint creates a PO with no mr_id/rfq_id — purchase_management/services.py:155–191, wired at routes/orders.py:25,55. From-RFQ only marks an MR ordered if mr_id is present — purchase_management/services.py:313–319.

Skippable

② RFQ + supplier quotes

All three links from the PO back to the RFQ are nullable, and supplier is satisfied by a free-text fallback. The PO can be authored directly.

Evidence: purchase_orders.rfq_id :86–91, winning_quotation_response_id :92–97, supplier_id :100 all nullable; supplier_name free-text fallback :101. Manual create path takes supplier_name without any supplier_id — purchase_management/services.py:135–191.

Cannot skip

③ Purchase Order + Phase

A GRN cannot exist without a PO and a phase — both FKs are NOT NULL with RESTRICT. Receipt is also blocked unless the PO has been approved to ORDERED.

Evidence: goods_receipt_notes.purchase_order_id & purchase_phase_id NOT NULL — goods_receipt_management/models.py:53–62; receivability guard rejects draft/cancelled/closed PO & draft/closed phase — purchase_management/services.py:745–754, 772–780; approval sets PO→ORDERED, phases→ORDERED — purchase_management/services.py:411–419.

Cannot skip (for purchase→stock)

④ Goods Receipt Note

On the purchase path, stock only enters via a posted GRN: each goods_receipt_items row hard-references a purchase_phase_item_id (NOT NULL), and posting drives received_quantity + the warehouse event.

Evidence: goods_receipt_items.purchase_phase_item_id NOT NULL — goods_receipt_management/models.py:120–124; warehouse IN movement is created only from a posted GRN dict — warehouse_management/services.py:1402–1458. Caveat: warehouse stock can be created without any GRN via a manual movement — see ⑤ alt.

Cannot skip

⑤ Stock Movement (ledger)

The stock_items balance is only ever changed through record_stock_movement. There is no other code path that writes on-hand quantity — so the ledger delta cannot be bypassed for any balance change (GRN receipt, manual entry, or stock-count adjustment all funnel through it).

Evidence: sole balance writers apply_incoming_balance / apply_outgoing_balance live inside record_stock_movement — warehouse_management/services.py:999–1060, 1122–1306; manual path create_manual_stock_movement (:1309–1347, route routes/warehouse.py:299–310) and stock-count post (:2003–2030) both call the same function.

Not enforced in code (worth flagging): the warehouse event is fire-and-forget — if the Celery dispatch fails or the module is missing, the GRN still commits as POSTED and stock movement is merely deferred (logged, recoverable via backfill_posted_goods_receipts) — goods_receipt_management/services.py:697–727, warehouse_management/services.py:2092–2120. So "GRN posted" does not transactionally guarantee "stock updated"; it guarantees it eventually. Also, nothing in the schema forces a PO to originate from an RFQ or an RFQ from an MR — those are conventions, not constraints.
