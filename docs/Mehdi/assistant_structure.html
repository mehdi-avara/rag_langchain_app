Request lifecycle · one chat message

1
User message arrives (any language)
Detect language; conduct the exchange in it, store values canonically. Attached files become FileAsset ids.
2
Build the intent set — RBAC-filtered RBAC
The registry is filtered by the caller's permissions first. The LLM never sees tasks the user can't access (no leak). Same filtered set the // slash menu uses.
3
Route the intent
Classify into one module task (plus general / clarify). Large registry → two-stage hierarchical routing: which module, then which task.
4
Read path read  or  Write path draft
Reads (search / summarize / ask) run the service and stream the answer with citations. Writes never touch the DB — the assistant builds a Draft with target_action, a pre-filled payload, and a commit target (the module's own endpoint + method + permission).
5
User reviews the rendered draft, edits, presses confirm
Chat text never commits — "yes / do it" in prose does nothing. The confirm button lives in the frontend.
6
Frontend POSTs directly to the module endpoint RBAC
The frontend sends the final payload to the module's own create/update endpoint (e.g. POST /financial/receipts) — same path the UI uses, enforcing RBAC + validation. The write never touches the assistant server.
7
Frontend notifies the assistant → POST /assistant/drafts/{id}/committed
Bookkeeping only: the assistant verifies draft ownership, marks it committed, stores committed_entity_ref, logs it to history. No domain write, no domain-RBAC re-check.

The module tool contract · ModuleToolSet (§12.4) · four seams

Each module exposes these four seams, each wrapping an existing service function. There is no commit_draft — the assistant never writes domain data; the frontend commits through the module's own endpoint. The agent reaches the module only through this adapter.

Reads use in-process service calls, never loopback HTTP (§12.4.1) — refactor read route logic into services.py and call it from both the route and the adapter. Writes need no assistant-side path: the frontend commits through the module's existing create/update route.

Architecture invariant · one agent, not one per module

✓ One compiled agent + registry
Adding a module adds adapter functions, not another live agent. Prompt stays small via (a) RBAC-filtering and (b) hierarchical routing.
✗ Per-module agents
Would still need a top-level router, duplicate the draft framework / checkpointer / streaming, and break cross-module tasks (no agent sees both modules).
If the registry grows too large for flat routing, recommend hierarchical routing as a Core change (§D) — never split the agent. Capabilities not covered by the contract are flagged as Core changes, never bolted onto a module.
